# API Quality Guard 架构规划

> 版本：v0.2（2026-10-12 四大模块重组）
> 定位：面向 Java 后端的 API 自动化测试与质量守护平台——导入接口文档 → 执行测试 → 质量评分 → 门禁判定 → AI 分析报告。

## 1. 四大模块总览

| # | 模块 | 包 | 职责 | 核心产物 |
| --- | --- | --- | --- | --- |
| 1 | API 测试执行 | `module.testexec` | 导入 Swagger / OpenAPI 接口定义；配置质量规则与自动化测试用例；HttpClient 执行接口测试 | `api_definition`、`test_case`、`test_run`、`test_result` 数据 |
| 2 | 质量评分 | `module.scoring` | 断言判定；质量评分计算；历史执行记录查询 | `test_run.score` 评分与明细 |
| 3 | 质量门禁 | `module.gate` | 质量门禁 API（阈值判定）；简单 CI 流水线集成 | 门禁检查结论、CI 产物 |
| 4 | AI 分析与报告 | `module.ai` | AI 故障诊断、AI 用例增强、测试报告与实验评估 | 结构化诊断、AI 候选用例、报告指标 |

### 模块依赖与数据流

```
┌─────────────────────────────────────────────┐
│ 1. 测试执行 testexec                         │
│   definition 导入/解析 ──> casegen 用例/规则  │
│        └──> plan 计划 ──> runner 执行(快照)   │
└──────────────────┬──────────────────────────┘
                   │ test_run / test_result（快照 + 断言明细）
                   ▼
┌─────────────────────────────────────────────┐
│ 2. 质量评分 scoring                          │
│   assertion 断言判定 ──> calculator 评分      │
│        └──> record 历史执行记录查询           │
└──────────────────┬──────────────────────────┘
                   │ score + 评分明细
                   ▼
┌─────────────────────────────────────────────┐
│ 3. 质量门禁 gate                             │
│   阈值判定 API ──> CI 流水线集成（通过/拦截） │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ 4. AI 分析与报告 ai（旁路，不参与判定）       │
│   读 run/result/score ──> diagnosis 诊断      │
│   enhance AI 用例（写回 test_case）           │
│   report 报告与实验评估                       │
└─────────────────────────────────────────────┘
```

两点说明：

- **断言的归属**：断言引擎代码放在 `scoring.assertion`（归属模块 2），但其运行时机在模块 1 的执行链路中——用例执行 → 断言判定 → 写入 `test_result.status`。这是"代码归属"与"运行时调用"的区别。
- **AI 的边界**：模块 4 只读执行数据、产出建议，不写 `test_result` 的判定结果，不参与评分和门禁。

│   │   ├── assertion/       #   断言引擎（你亲写）
│   │   ├── calculator/      #   评分计算
│   │   └── record/          #   历史执行记录查询
│   ├── gate/                # 模块 3：质量门禁
│   └── ai/                  # 模块 4：AI 分析与报告
│       ├── diagnosis/       #   AI 故障诊断（你亲写）

每个子域按需增加 `controller / service / mapper / entity / dto / vo`，不预建空类。

## 4. 质量评分口径（初稿，待确认）

三个维度各自 0~100 分，加权合成总分：

| 维度 | 计算方式 | 默认权重 |
| --- | --- | --- |
| 功能通过率 | 断言通过的用例数 / 执行用例总数 × 100 | 70% |
| 性能达标率 | 响应时间断言通过的用例数 / 含响应时间断言的用例数 × 100（无响应时间断言时该维度不计入，权重按比例摊回其他维度） | 15% |
| 稳定性 | (1 − ERROR 用例数 / 总用例数) × 100 | 15% |

- 总分 = Σ(维度分 × 权重)，保留 1 位小数。
- 等级：≥90 优秀 / 80~89 良好 / 60~79 及格 / <60 不合格。
- 权重与阈值支持计划级覆盖（存入 `execution_config`），默认值集中在评分规则配置中。
- `score_detail` 记录各维度得分、权重与计算基数，保证评分可解释、可复现。

## 5. 质量门禁规则（初稿，待确认）

门禁 = 对一次运行结果做阈值判定，输出通过/拦截结论与违规明细：

| 默认规则 | 阈值 |
| --- | --- |
| 质量总分达标 | score ≥ 80 |
| 执行异常零容忍 | error_count = 0 |
| 失败用例数上限 | failed_count ≤ 0（可配置） |

- 计划级可通过 `execution_config.gate` 覆盖阈值。
- 判定输出：`{ passed, score, threshold, violations: ["error_count = 2，超过上限 0", ...] }`。
- 每次门禁调用写入 `quality_gate_record`（含当时阈值快照），供审计与历史查询。

### CI 流水线集成（简单版）

产物：一个 GitHub Actions 示例 + 一个调用脚本（`scripts/ci/quality-gate.sh`），流程四步：

```
1. 启动服务（docker compose up，含被测服务）
2. POST /api/plans/{id}/runs          → 拿到 runId
3. 轮询 GET /api/runs/{id} 直到终态
4. POST /api/gates/check { runId }    → passed=false 则流水线失败（exit 1）
```

## 6. 开发里程碑

| 里程碑 | 内容 | 你亲写的部分 |
| --- | --- | --- |
| M1 API 测试执行 | ① 接口定义导入与管理（OpenAPI 解析）→ ② 用例配置与规则生成 → ③ 执行引擎 + 断言引擎（执行链路闭环）→ ④ 测试计划与并发调度 | ②生成引擎、③执行引擎、③断言引擎、④调度 |
| M2 质量评分 | 评分计算 + 历史执行记录查询（评分随 run 展示） | 评分算法口径由你确认后实现 |
| M3 质量门禁 | 门禁检查 API + 记录表 + CI 流水线集成 | 门禁规则实现 |
| M4 AI 分析与报告 | AI 故障诊断 → AI 用例增强 → 报告与实验评估 | 诊断上下文与输出校验 |
| M5 部署完善 | Docker Compose、文档完善、回归测试 | —— |

M1 内容最多，内部按 ①②③④ 四个小步推进，每步延续"设计→骨架→你实现→审查"的流程。
